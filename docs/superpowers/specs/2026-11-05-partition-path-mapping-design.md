# 基于实际挂载表的现有分区路径映射

日期：2026-11-05
状态：设计草案；用户已确认冲突分区跳过报错，并要求纳入上游改进实施计划。尚未开始实现。

## 意图与已确认决定

用户希望用设备实际挂载表校正现有分区的路径映射，而非自动发现名单以外的新分区。
已选择统一路径映射方向。用户明确要求：当 /vendor 与 /system/vendor 等候选路径是不同的树时，将该分区跳过并报错。

以下未由用户逐项指定的细节为设计建议，等待整份设计确认。

## 现状与范围

检查基线：origin/dev d39c5925；当前工作树 dev 落后 4 个提交，差异是依赖与版本资料，本文涉及的 Rust 分区实现无差异。

当前 Config::scan_partition_names 根据 MANAGED_PARTITIONS 中根目录是否存在决定扫描范围；extra_mount 另有准入校验。
pipeline::detect_promoted_partitions 通过目录和符号链接检查生成集合，plan::map_target 根据集合将 system/<分区> 提升至 /<分区>。
集合无法表达反向映射，且目录存在不证明它是实际独立挂载点。挂载表已用于运行时确认和 OverlayFS 子挂载恢复，但不统一参与上述判断。

目标：在现有名单内统一确定模块的逻辑路径与目标路径；OverlayFS、Magic Mount、VFS 共用；启动、查询和热操作语义一致。

不增加自动 OEM 分区发现；不扩展 extra_mount 的准入；不增加 WebUI 配置开关；不挂载块设备、不修改分区、不移动模块文件。
不解析模块内每个普通文件的符号链接以改写目标；只解析设备分区根的布局别名。
此前调查的 xattr CI 失败为独立事项，不包含在此设计中。

## 方案比较

1. 在现有提升集合上补充挂载点判断：改动较小，但不能表达 /vendor -> /system/vendor，难以统一处理错误与别名。
2. 统一分区路径映射：用挂载表和设备路径证据生成映射与分区错误，所有后端消费同一结果。用户已同意这一方向。

不采用块设备名称猜测分区：设备号和挂载源名称都不能单独决定用户可见目标路径。

## 数据与职责

引入只读布局发现层，输出不可变 PartitionLayout（名称由实现者决定）：

- 每个现有逻辑分区的两个模块入口（<分区>、system/<分区>）、最终设备根路径、判断依据。
- 已证实的路径别名关系和相关可见挂载身份。
- 无法使用的分区及结构化原因（冲突、断链、循环、权限或证据不足等）。

保留 system 本身的规划入口；分区标签与最终路径分离，例如 vendor 的目标可以是 /system/vendor。
extra_mount 仍使用原准入条件，通过后沿用显式根路径，不对其增加两入口自动合并。
扫描、规划、状态输出共用布局对象，不各自重算提升集合。

## 发现时机与证据

启动在进入 init 挂载命名空间、取得操作锁以后，任何新模块挂载或 VFS 规则应用之前发现布局；同一轮只生成一份布局快照。
优先复用 boot session 的应用前挂载表快照，避免前后两次读取产生不一致。
操作开始时已经存在的外部 overlay/bind mount 视为当前可见布局，不通过卸载或穿透它们推测“原生”布局。

路径证据包括：symlink_metadata、分区根符号链接链的有限解析、最终目录身份；挂载证据包括精确挂载点及其覆盖祖先。
MountEntry 如有需要扩展 mountinfo 的 filesystem root 和 parent id 字段；设备号相同不表示同一子树。
两条非符号链接路径的合并须确认最终目录身份相同（设备号和 inode），并与可见挂载的设备号、filesystem root 相容。
设计者决定：bind 别名还必须验证整棵可见子树的后代挂载等价。将后代挂载换算为相对分区根的路径，比较实际覆盖范围及相应目录/文件身份；挂载 id、传播组等不决定内容等价。仅根身份相同，但一边单独挂载了 etc 等后代时，判定布局冲突并跳过。无法确认后代拓扑也不得合并。符号链接直接解析到同一路径的情况不需要对同一棵树重复比较。
对同点堆叠挂载必须识别实际可见挂载；不得用最大 mount id 或任意第一条记录代替可见性判断。证据不足时不合并，分区报错跳过。
mount id 仅作快照内定位与诊断，不作为跨操作布局是否变化的唯一依据。

缺少独立挂载点不等于目标不存在：/system/vendor 可以是 system 文件系统中的正常子目录。
根目录符号链接链必须有效且指向允许的分区布局目标；循环、断链或逃向 /data、/proc 等无关树时，该分区不可用。
允许目标的精确定义：当前逻辑分区的 /<分区>、/system/<分区>，以及通过有效 system 根布局别名解析得到的等价路径；不接受任意存在目录。

## 映射决策表

| 可确认布局 | 决定 |
| --- | --- |
| /system/vendor -> /vendor，两者证据相容 | 两种模块入口映射至 /vendor |
| /vendor -> /system/vendor，两者证据相容 | 两种模块入口映射至 /system/vendor |
| 两者是同一子树的 bind 别名，根身份与后代可见挂载拓扑均等价 | 优先 /vendor 的精确可见挂载；其次 /system/vendor 的精确可见挂载；均无独立挂载时优先 /system/vendor |
| 只有 /system/vendor 是有效目录 | 两种模块入口映射至 /system/vendor |
| 只有 /vendor 有效且有精确可见挂载 | 两种模块入口映射至 /vendor |
| 只有 /vendor 是普通目录，没有精确挂载或别名证据 | 证据不足，分区跳过并报错 |
| 两者存在但确认是不同子树，或不能证明等价 | 分区跳过并报错，不选择其中一个 |
| 两者都不存在 | 标记不可用；有启用模块请求该分区时报告缺失并跳过 |
| 断链、循环、权限错误或不允许的目标 | 分区跳过并报错 |

对其他现有名单分区应用同样规则；取消 odm 仅凭根目录存在就提升的特殊处理。
规则里的 vendor 是例子，不通过分区名称或文件系统类型强行认定等价。

## 扫描、规则与规划

扫描现有名单对应的模块真实目录，包括只有 system/<分区> 存在的设备布局；不能因为 /<分区> 不存在就漏掉模块顶层目录。
对不可用分区也保留足够的模块请求信息，用于解释哪些内容被跳过。禁用、remove、skip_mount、黑名单和已 ignore 的内容不构成挂载失败请求。
遵守现有模块扫描不跟随根别名、只读模块目录的约束。仅将实际指向模块内对应布局入口的链接认作兼容别名；其他链接保留原语义或按现有校验拒绝，不按名字静默删除。

路径规则仍按原模块相对路径匹配，之后再映射目标。source_path 和原相对路径不改写。
映射后进行所有后端的目标冲突检测；来自两个真实模块目录的贡献不得因为映射相同就静默去重。
只有已证实的模块布局别名去重，历史自嵌套别名也需要确认证据；真实文件内容不因名字相似而丢弃。
分区根边界、.replace、whiteout、整模块 OverlayFS 拆分和浅层 staging 都使用同一布局语义。

跳过分区意味着该分区两个逻辑入口下的全部贡献对三个后端均不可执行，跨模块也一样。
任何祖先目录操作都不得间接带入被拒绝的分区。整树 overlay 必须从经过过滤的共享树构建 staging，必要时下拆操作；不能实现隔离的祖先 .replace/覆盖操作也跳过并说明原因，其他独立分支继续。
不得直接使用包含拒绝分区内容的原模块目录作为宽范围 lowerdir 或 Magic Mount 替换源。

## 错误、状态和返回语义

单个分区不可用为局部降级：执行其他有效分区，提交其真实所有权；日志记录 error，不在最终返回处用全局 Err 触发现有整轮回滚。
运行状态增加兼容旧数据的默认字段，记录分区、候选路径、原因和受影响模块；模块输出展示“部分挂载，某分区跳过”，全被跳过时不标记为已挂载。
此类错误为本轮运行诊断，不在模块目录写入 mount_error 标记，也不持久修改配置或禁用模块。
分区诊断使用独立字段，不自动设置现有 suggest_ignore，不因它建议永久忽略整个模块；与现有 mount_error 标记错误可同时展示且互不清除。
WebUI 模块列表须展示部分失败原因，状态查询提供结构化详细证据；旧字段的已挂载含义保持“至少一个效果已确认”，不能用它表示完整成功。
单分区错误的管线可正常提交并返回成功，但运行状态必须明确 degraded 及错误摘要，不能展示整轮无错误成功。

全局挂载表读取失败为布局发现失败：在新挂载/规则应用前终止，保留失败阶段与原因，不退回旧猜测逻辑。
其他执行和回滚错误继续遵循现有事务语义。

## 热操作与查询

设计者决定：启动时将现有名单内全部分区的发现结果（包括可用、缺失、冲突及必要身份依据）记录至同一 boot ledger，而非仅保存有模块内容的分区。新增字段带默认值。
热加载前重新发现当前布局；将即将使用的分区与保存的映射比较。无关分区变化不阻止操作，同分区只发生堆叠挂载 id 变化不算映射变化。
本模块已应用的覆盖可能改变目录身份和后代挂载拓扑：仅当实际效果身份仍与所有权账本吻合时，将其视作预期变化并关联保存基线；不能据此忽略身份不明的外部覆盖。不能证明变化来自已拥有的效果时，拒绝新加载。
首次热加载一个启动时未使用的分区也与该分区的启动基线比较；从缺失/冲突变为可用也属于变化，提示重启，不在本轮首次使用时悄悄接受新布局。
发现已加载分区的路径映射变化或冲突时，拒绝该分区的新规则，明确提示需重启；本轮不得尝试迁移已经应用的规则。
临时 load 的分区局部跳过与启动一致；已含 Magic/Overlay 的模块仍保持现有不允许热加载的规则，不得通过先过滤出错分支将混合模块变成纯 VFS 来绕过限制。
临时 load 全部目标被跳过时返回错误且不变更规则/所有权；部分成功时在现有响应增加 degraded 与错误摘要，避免只返回 ok: true。只有启用且非 ignore 的模块实际请求了不可用分区，才使该轮进入 degraded。
热 reload 先完整预检：原来拥有规则的分区如变成不可用，不删除旧规则后再“部分重载”；此时拒绝 reload，保留原所有权。
卸载只按保存的实际目标和规则身份清理，即使当前布局解析失败仍允许尝试原有所有权校验与卸载，不重新推算路径。
旧 ledger 没有布局数据时：允许原有卸载；新增 load/reload 拒绝并提示重启，以免迁移中猜测已加载布局。
模块只读查询优先展示本次启动保存的映射和诊断；需要当前预览时明确标为预览，不重写已加载路径、不修改 ledger、不将查询失败伪装为空计划。

## 验收与测试

- 决策表每种布局都有独立夹具，覆盖正反符号链接、循环/断链、普通子目录、同子树 bind、根相同但后代挂载不同的 bind、不同 root 的同设备 bind 和同点堆叠。
- 同一逻辑分区的两种模块布局在三种后端产生相同目标，source 与规则匹配保持原值。
- 两棵不同树时该分区零效果；混合 system/vendor 模块的 system 独立分支仍执行，错误关联正确模块。
- 祖先 overlay、Magic 替换、.replace 和 whiteout 不泄漏被拒绝分区；无法隔离的祖先操作有明确诊断。
- 别名去重不吞掉真实内容，不新引入分区根覆盖；现有根拆分和后端冲突回归通过。
- 部分/全部跳过时模块状态、degraded、所有权与实际效果一致，旧状态/ledger 读取保持兼容。
- 热布局漂移拒绝新规则，首次使用也对比启动基线；reload 预检失败保留旧规则；旧 ledger 卸载仍可用；挂载表全局读取失败在执行前停止。
- 适用的 Rust 单元/CLI、格式和 Clippy、WebUI 类型/展示测试通过；有 Linux 环境时增加隔离 mount namespace 集成验证。
- 主机和 CI 通过不代表 Android 真机已验证；真机覆盖常见独立分区布局与 system 内目录布局，届时分别记录结果。

## 纳入的上游经验与实施顺序

用户于 2026-11-05 要求将上游评估结果加入计划。
Mountify [8ba7163f7a49](https://github.com/backslashxx/mountify/commit/8ba7163f7a49a70c25ab96193fe8ccd1f21773a7) 的“存在子挂载时向下拆分”纳入本设计：在应用父 overlay 前按快照识别边界，优先分解成不遮住子挂载的操作。
保留模块新增文件、符号链接、whiteout 与 .replace 的语义，不照搬其对不存在目标直接跳过的 shell 行为。无法保留语义的操作局部跳过并报告，不能用执行后重建失败掩盖布局损失。
路径映射和子挂载保护使用同一应用前快照；分区根可用不代表所有后代挂载都能安全覆盖。

其他上游改进单独规划，见 [上游选择性吸收设计](2026-11-05-upstream-improvements-design.md)。
推荐顺序：VFS 生命周期与 UID 边界验证 → xattr 特性探测 → 本设计的路径映射和子挂载保护 → .remove → 源文件身份研究。
其中 VFS 与分区映射可独立交付，.remove 在分区映射合入后开发，避免在规划器上并行维护两套规则。

实施计划：[分区映射与子挂载保护](../plans/2026-11-05-partition-path-mapping.md)、[VFS 上游改进](../plans/2026-11-05-vfs-upstream-improvements.md)、[.remove 兼容](../plans/2026-11-05-remove-marker-compatibility.md)。
